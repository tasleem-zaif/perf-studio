## Architecture

Peako/PerfStudio is a **performance-testing platform**: users import an API definition (Postman collection / Swagger / cURL / raw JSON), the platform fires the endpoints live ("pre-run") to learn auth tokens, correlate values between requests, and observe response shapes, a **deterministic template builder** (not AI — see below) generates a JMeter or K6 load-test script from all of that plus user-configured rules/test-data, and the script is executed either natively, in a spawned Docker container, or via an external CI provider (GitLab/GitHub Actions/Bitbucket). Results are parsed, evaluated against pass/fail rules, emailed, and rendered as analytics dashboards / PDF reports.

**Script generation is deterministic, not AI-driven, for both engines.** `testSuites.js`'s `generateJmx()`/`generateK6()` build the script directly (`buildJmxTemplate()`/`buildK6Template()`) — no LLM call in either path. This wasn't always true for k6: it used to hand the AI a raw JSON dump of pre-run responses and a prompt asking it to "extract dynamic values and pass them to subsequent requests," which was non-deterministic and is the reason a collection with no `{{var}}`/test-data file used to just fail outright once recorded literal values (tokens, IDs) went stale. k6 was rewritten to use the same request-builder + correlation pipeline JMX already used. AI is still used elsewhere: **auto-heal diagnosis** (`autoHealer.js`, fixing an already-generated script that fails at runtime) and **pre-run's per-endpoint "Fix with AI"** (`routes/ai.js`'s `/pre-run/heal`, natural-language-guided one-off fixes) — never for the initial script build.

**Full request correlation** (`utils/correlationEngine.js` + `utils/scriptCorrelation.js` + `utils/fieldGenerators.js` + `utils/transforms.js`) is what makes a 100%-hardcoded recorded collection (no `{{var}}`, no env file, no test data) still produce a script that works on every run, not just once: pre-run detects which recorded literals in a later request are actually values an earlier response produced (body fields, response headers, form-urlencoded bodies — not just auth tokens), a human confirms/rejects/manually-adds rules via a review panel, and confirmed rules get burned into the generated script as real extractors (`JSONPostProcessor`/`RegexExtractor` for JMX, `res.json()`/`res.headers` accessors for k6) plus literal substitutions — so every run captures its own fresh values instead of replaying whatever was true at record time. `utils/fieldGenerators.js` covers the complementary case (a value with no correlation source at all, e.g. a recorded unique email) via `${__UUID()}`/`Date.now()`-style generators. `utils/transforms.js` covers a target needing a *derived* version of a correlated value (md5/sha1/sha256/urlEncode/urlDecode/upperCase/lowerCase — a whitelisted set, not arbitrary scripting) rather than a verbatim copy. See the Business Logic section below for the full mechanics and the real bugs this uncovered.

```
Browser (React SPA)
   │ axios, JWT in Authorization header
   ▼
Express API (backend/src/index.js) ── mounts ~23 route modules under /api/*
   │

   ├─ Filesystem workspaces (git-workspaces/<Project>/<admin|user-N>/<Collection>/<Env>/{config,testData,script,results})
   ├─ AI provider (OpenAI/Anthropic) ── script generation + auto-heal diagnosis
   ├─ JMeter / K6 binaries (native) or Docker containers ── test execution
   ├─ Git provider (GitHub/GitLab/Bitbucket) ── script versioning, PRs, CI triggers
   └─ SMTP ── alert emails, invites, password reset
```

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the full Mermaid diagrams (system architecture, data model, auto-heal flow, CI pipeline flow, security model, multi-env isolation).

**Multi-environment / multi-tenant isolation model:**
- Every project has one workspace folder per **environment** (QA/Staging/UAT/Production) and one per **actor**: an `admin/` workspace (org admin, pushes to `main`) and one `user-<id>/` workspace per regular user (pushes to `users/<name>`, merges via PR).
- Config, test data, scripts, and results are always scoped by `collection_id + env` at the DB layer — switching env in the UI can never leak another env's data.

## Backend Services (utils/)

| File | Purpose |
|---|---|
| `aiClient.js` | Single entry point for LLM calls (`callAi(userId, systemPrompt, userPrompt, purpose)`). Routes to OpenAI or Anthropic based on the admin's saved `ai_settings`; decrypts the stored API key; `purpose='script'` vs `'heal'` selects a different model. Anthropic is called through an OpenAI-compatible endpoint. Temperature fixed at 0.2. |
| `autoHealer.js` | **1-attempt** (changed from 3 — see the "auto-heal restricted to 1 automatic attempt" entry in Business Logic below), 2-phase auto-heal loop for failed runs. `diagnoseWithAi()` first runs a **deterministic mechanical check** (`tryFixTemplateVars`) for literal Postman `{{var}}` tokens still baked into the script — JMeter/K6 don't support that syntax at all, so any occurrence is a guaranteed cause with zero ambiguity; it's fixed directly (real value from `collection_env_config.variables` if known, else a JMeter `${var}` reference) without spending an AI call. Only if no `{{var}}` is found does it fall through to classifying JTL errors (DNS, auth/correlation, assertion, variable-reference, request-malformed, or ≥70% infra failures) and asking the AI for a JSON fix (`{issue, fix, fix_type, fixed_script}`). Either way: applies the fix, quick-verifies (3 VUsers/20s), then does a full re-run with original params. Max 1 automatic attempt; a follow-up requires the user to click "Heal Again" with a steering instruction. Rejects fixes that drop any sampler/endpoint. This module itself is now dead code for local execution (retired, HTTP 410) — it's still live and shared by CI heal (`ciPipeline.js`'s `healCycleCI()`, which imports `diagnoseWithAi`), which is the only reachable heal path today. |
| `preRunEngine.js` | Shared `{{var}}`-handling engine, used by pre-run (`ai.js`), script generation (`testSuites.js`), and auto-heal (`autoHealer.js`) so the three don't carry independent (and inevitably divergent) copies of the same substitution logic: `substituteVars`/`findMissingVars` (live pre-run requests — resolved value or left as `{{var}}` for the caller to report missing), `resolveForScript` (generated scripts — resolved value or falls back to a JMeter `${var}` reference, never literal unsubstituted text), `resolveUrlSet` (endpoint URL → `{protocol,host,port}`, handles multi-host `{{var}}` resolution + a port-variable fallback), `fireEndpoint`/token/cookie extraction for pre-run itself. `fireEndpointsWithCorrelation` (the sequential, correlation-aware pre-run path) fires endpoints in a **topologically sorted order** (`topologicalFireOrder` — Kahn's algorithm, ties broken by lowest original index), not raw collection order — **fixed a real bug**: a collection recorded by clicking around a real app (many endpoints across unrelated flows) is not guaranteed to have its source endpoint (e.g. "Login") recorded before every endpoint that correlates from it; firing strictly in recorded order silently ran the dependent endpoint before its source ever captured a live value, falling back to the stale recorded literal and failing every time, no matter how many times pre-run reran. A collection already in valid dependency order fires in that same order, unchanged. |
| `ruleEvaluator.js` | Parses a JTL file into metrics (error rate, avg RT, P90/P95, throughput) and evaluates them against the project's `rules` rows (`>`, `>=`, `<`, `<=`, `==`, `between`). `severity=error` rules must all pass for the run to pass; `warn` rules are logged only. |
| `testRunner.js` | Spawns the actual JMeter/K6 subprocess natively, patches runtime params into the JMX, streams stdout, and calls `ruleEvaluator` on the resulting JTL. Locates binaries via a fallback chain (bundled → common install paths → PATH). |
| `generateAnalyticsPdf.js` | Renders a 6-page analytics report (Summary, Dashboard, Transactions, Trend, Resource Utilization, Errors) as HTML with inlined Chart.js, screenshots each page via Puppeteer, stitches into a PDF with `pdfkit`. |
| `emailUtils.js` | Three email types: post-run summary (KPI grid + PDF), mid-run rule-breach alert, post-run violation summary. Resolves SMTP config from the user's own settings, falling back to an org/super admin's SMTP config; merges recipients from user, admin, and project-specific lists. |
| `projectFolders.js` | Computes/creates the `git-workspaces/<Project>/<admin|user-N>/...` folder tree; distinguishes admin vs. per-user workspaces; zips + deletes on project removal. |
| `ownsProject.js` | Central authorization check — owner, project-assignment, org-admin-of-owner's-org, or super-admin all grant access. |
| `configWriter.js` | Regenerates each collection/env's `config.json` snapshot (project info, rules, test plans, merged URL config) whenever rules/config/collections change. |
| `parseCollection.js` | Converts an uploaded Postman v2.1 collection or Swagger/OpenAPI spec into Peako's internal flat endpoint list (`{name, folder, method, url, headers, body, queryParams}`). **Does not execute Postman pre-request scripts or resolve `{{var}}` — see Business Logic note below.** |
| `resetSequence.js` | After bulk deletes, resets a Postgres `SERIAL` sequence to `MAX(id)` to avoid ID gaps. |
| `correlationEngine.js` | **Detection only** (pure functions, no DB/network) for full request correlation. `detectCorrelations(endpoints, preRunData)` scans every later endpoint's URL path segment/query param/header/body for a literal value that exactly matches (or, for headers, is contained within) a value an earlier endpoint's response produced — body fields, response headers (`HEADER_SOURCE_DENYLIST` excludes boilerplate like `content-type`/`date`/`set-cookie`), and form-urlencoded bodies (`parseBodyToObject`), not just the old fixed `TOKEN_KEYS` list. Each candidate gets a `confidence` (`'high'` if source/target field names looked related, or the match came from a header — headers are always high confidence, since a header's own key name never resembles the source field name; `'low'` otherwise) and `status: 'auto'`. `mergeRules(previous, fresh)` reconciles a fresh detection pass against previously stored rules so a human's confirm/reject/manual-edit survives re-running pre-run — **fixed a real bug**: a confirmed/rejected rule used to survive re-detection only if THIS run's fresh pass still happened to re-propose the exact same id; for a volatile source value (a session token, different on every live run) that coincidence holds at most once, so a confirmed rule would silently vanish from storage on the very next pre-run. Now confirmed/rejected rules always survive, same as manual ones already did. `describeAllCapturedFields(priorResults, endpoints)` powers `ai.js`'s heal-prompt field listing (see below). `reindexAfterEndpointRemoval(envCfg, removedIndices)` — after `routes/collections.js`'s endpoint-delete route removes one or more endpoints from `json_content`, re-derives every `correlationRule`/`fieldGenerator`/`endpointOverride`'s endpoint-index references (dropping any that pointed at a removed index, shifting any that pointed after one) so they don't silently misdirect at the wrong endpoint post-deletion; applied to every env's config row for the collection. |
| `scriptCorrelation.js` | Turns confirmed rules into what a script generator needs: `filterApplicableRules()` (only `'confirmed'` or unreviewed `'high'`-confidence rules are ever burned into a script), `groupRulesBySource()`/`groupRulesByTarget()` (endpoint-index → extractor list / target-rule list), `substituteCorrelatedLiterals(normalized, targetRules, engine)` (rewrites a recorded literal to a `${varName}` reference — JMeter's `${}` property syntax and a k6 JS template literal's `${}` interpolation are textually identical, so the same function serves both engines; a rule with an optional `transform` produces a transform-wrapped expression instead via `transforms.js`), `jsonPathToOptionalChain()`/`k6HeaderAccessor()` (k6-side extraction/header-lookup codegen). **Fixed a real bug, found via a live end-to-end test against a real target app**: inject mode (`rule.value === null`) into a literal `cookie` header target from a `sourceLocation: 'cookie'` rule used to set the header to the bare captured value — but a real HTTP `Cookie` request header is a `name=value` pair per RFC 6265, so a bare value is never recognized by any server-side cookie parser and the request 401s regardless of how fresh the value is. Now reconstructs `${sourceJsonPath}=${ref}` specifically when the target header name is literally `cookie` (case-insensitive) and the source was cookie-sourced; any other header target (e.g. a custom `X-Session-Token`) still gets the bare value, unchanged. `preRunEngine.js`'s `applyLiveCorrelatedValues` has the matching live-fire-side fix. |
| `fieldGenerators.js` | For a recorded literal with **no correlation source at all** (never appeared in any earlier response — a unique email/username/idempotency key) — always user-attached via a manual rule, never auto-detected (auto-detection can't infer "this needs to be unique"). Fixed registry: `uuid`/`timestamp`/`unique` (thread+timestamp combo), each with a JMeter-function form (`${__UUID()}`, `${__time()}`) and a k6-JS form (`crypto.randomUUID()`, `Date.now()`). |
| `transforms.js` | For a target needing a **derived** version of a correlated value (not a verbatim copy) — e.g. "the md5 of the login response's userId." Always manually authored (a transformed value never literally matches, so detection can't propose it). Whitelisted set only, not arbitrary scripting: `md5`/`sha1`/`sha256` (JMeter `__digest`, k6 `k6/crypto`), `urlEncode`/`urlDecode` (`__urlencode`/`__urldecode`, `encodeURIComponent`/`decodeURIComponent`), `upperCase`/`lowerCase` (`__changeCase`, `.toUpperCase()`/`.toLowerCase()`). Every JMeter expression was verified against the real user manual, not guessed — `__base64Encode`/`__base64Decode` do **not** exist as native JMeter functions (confirmed absent), so base64 is deliberately excluded rather than shipped via an unreliable JSR223 fallback. |
| `s3Sync.js` (**uncommitted — see "S3 migration" below**) | Core S3 client wrapper, gated entirely behind `S3_SYNC_ENABLED` + `S3_BUCKET` (`isEnabled()` — every exported function is a no-op returning `{ok:false, skipped:true}` when unset). Two API layers: (1) **path-based** (original, still used by `workspaceLifecycle.js`/git-workspace mirroring): `uploadFile`/`downloadFile`/`deleteObject`/`existsInS3`/`uploadDir`/`downloadDir`/`uploadWorkingTree`/`deleteDir`, all deriving their S3 key from a local path via `toKey(localPath, orgSlug)` (namespaces under `<prefix>/<org>/...`, resolving which of the three non-nested roots `GIT_WORKSPACES_ROOT`/`PROJECTS_ROOT`/`BACKUPS_ROOT` a path belongs to). (2) **raw key-based** (added for `resultsStore.js` — no local path involved at all): `putBuffer`/`getBuffer`/`existsKey`/`listSubPrefixes`/`listAllKeys`/`deleteAllUnderPrefix`, operating directly on an explicit S3 key. `orgSlug` always comes from `projectFolders.js`'s `resolveOrgSlugForProject()`, never reverse-parsed from a path. **Added (Phase 3, uncommitted)**: `assertBucketReachable()` (throws if S3 isn't configured or the bucket isn't reachable — `index.js`'s boot check), `warnIfInsecureCredentials()` (non-blocking production nudge toward an instance/task IAM role over static keys), and every failure path now also calls `opsAlert.js`'s `alertOpsFailure()` (webhook/email) instead of leaving alerting to each caller's own `console.error`. |
| `opsAlert.js` (**new, uncommitted — see "S3 migration" below**) | Real alerting for S3 operational failures. `alertOpsFailure(kind, subject, details)` — fire-and-forget, never throws, rate-limited per `kind` (`OPS_ALERT_RATE_LIMIT_MS`, default 5 min, reports a suppressed-count when it resumes). Two channels, either optional: a webhook (`OPS_ALERT_WEBHOOK_URL`, JSON POST) and email (reuses the existing SMTP alert infra — any org_admin/super_admin's saved `alert_configs` row via `emailUtils.js`'s exported `getAlertConfig`/`createTransport`, sent to every org_admin/super_admin). Tested in `opsAlert.test.js`. |
| `workspaceLifecycle.js` (**uncommitted — see "S3 migration" below**) | The move/hydrate engine sitting on top of `s3Sync.js`'s path-based API, specific to git.js's per-actor workspaces. `markWorkspaceSyncedAfterPush({gitDir,orgSlug})` — uploads, and only on full success writes a marker (outside gitDir, under `git-workspaces/_sync-markers/`, so `git add .` never picks it up) recording the confirmed HEAD + timestamp. `ensureWorkspaceHydrated({gitDir,orgSlug,restoreGitContent})` — the retrieval-side gate: no-ops instantly if already warm, otherwise locks (`withWorkspaceLock`, per-`gitDir`) and restores via the caller-supplied `restoreGitContent` (git.js passes its own `ensureUserWorkspace`) plus `s3Sync.downloadDir()` for anything git doesn't track. `sweepStaleWorkspaces()` — the only function that deletes anything; skips within `S3_WORKSPACE_COOLDOWN_MS` of the marker, skips if HEAD moved or the tree is dirty since, only then `rmSync`s. Fully covered by real end-to-end tests (`workspaceLifecycle.test.js` — real bare-repo git remote, real filesystem, in-memory S3 double). **This module and its whole disk-cache-with-sweep model are superseded for anything NOT git-tracked** — see "S3 migration" below; still the plan for `git.js` itself pending the isomorphic-git rewrite. |
| `resultsStore.js` (**new, uncommitted — see "S3 migration" below**) | S3-only storage for everything under a run's `result_dir` (JTL, JMeter HTML report, analytics PDF) — **no local file exists at any point**, not even transiently. `result_dir` keeps its exact historical shape (a path-SHAPED naming string, e.g. `.../results/Run_5_...`) so every existing naming/run-numbering convention (`buildRunName.js`) is untouched, but it's now purely an S3 key prefix derived via `s3Sync.toKey()` — never created as a real directory. Consumed by `ciPipeline.js` (CI artifact sync), `execution.js` (report/PDF/ZIP-download routes), `autoHealer.js` (`buildContext()`'s JTL read for CI heal), `trend/metricsStore.js`. |

## Frontend Architecture

- **No Redux/Zustand** — all app state (`user`, `projects`, `activeProject/Collection/Env`, `page`) lives in `useState` at the top of `App.jsx` and is prop-drilled down. `ToastProvider`/`useToast` and a promise-based `useConfirm` are the only context-like abstractions.
- **Routing** is manual (no react-router visible from the report) — `page` state + `popstate` listener; a `ProjectWorkspace` wrapper renders project-scoped sub-pages (`collections`, `test-data`, `rules`, `config`, `test-suites`, `alerts`, `runner`, `analytics`, `reports`, `ai-config`, `git`) sharing `activeProject/Collection/Env` context.
- **Fixed: active-collection auto-select had a mount-timing race**. `ProjectWorkspace.jsx` auto-selects `collections[0]` as `activeCollection` (and its first env as `activeEnv`) via a `useEffect` — this is the **only** place either gets set anywhere in the file, there's no manual collection/env picker UI. The effect's dependency array was `[project?.id]` only, so if `project.collections` arrived asynchronously *after* that first run (a real, reproducible race — confirmed on a fresh login), no collection ever got auto-selected. Symptom: `Config.jsx` (and any other page needing `collection`/`env`) permanently fell back to its "no collection selected" branch — no EnvBar, no per-collection Environment Config/Variables section, even though the project genuinely had collections. Fixed by adding `collections.length` to the dependency array so the effect re-evaluates once the list actually arrives, not just once at mount.
- **Auth**: JWT stored in `localStorage` as `ps_token`, attached via an axios request interceptor; a 1-second heartbeat to `/api/auth/heartbeat` detects a session being taken over from another tab/device and force-logs-out; 401 responses clear storage and reload.
- **20 pages**: Dashboard, ProjectHome, ProjectWorkspace, Collections, Recorder, Rules, Runner, TestSuites, TestData, Config, Settings, Profile, Alerts, Analytics, Reports, GitPanel, PipelineConfig, Auth, ForgotPassword, ResetPassword, AcceptInvite.
- **Key components**: `Sidebar` (hierarchical project→collection→workflow-step nav), `EnvBar` (env pill selector on env-aware pages), `GitPanel` (status/diff/commit/branch/PR UI), `CopyCommandBlock` (extracted from Profile.jsx, reused by the org registry-token panel).
- **Collections.jsx's Pre-run Logs popup has a Correlations section** (not a `<Modal>` — see the custom-draggable-popup note below) alongside the per-endpoint response list: lists detected rules (source/target endpoint+field, confidence/status badges) with Confirm/Reject/**Delete** (the trash icon is unconditional now — every rule can be permanently deleted, not just `confidence === 'manual'` ones; deleting a redetectable auto rule isn't necessarily forever, since nothing protects a fully-removed id from `mergeRules` re-proposing it if the exact same value-match recurs on a later run — reject is the durable choice for those, delete is for "get it out of my list now"), and a manual "+ Add correlation" form for anything auto-detection missed — wired to `/api/ai/correlations*`. Source endpoint/location (body/header/cookie)/field-name (bare name or full jsonPath) on one side; **target endpoint is a multi-select checkbox list** (`manualForm.targetEndpointIndices`, not a single `<select>`) so one source can fan out into many target endpoints in one submit, plus target location/key, an "Always add this header, even on endpoints that never recorded it" checkbox (`injectIfMissing`, shown only for `targetLocation === 'header'`, sends `value: null` rules), varName, transform dropdown, and an explicit-value override (hidden while injecting, since there's no existing literal to override). The add call reports per-target `created`/`skipped` results, not all-or-nothing.
- **Each endpoint row in the same popup has its own delete action** (`deleteEndpoint`, wired to `POST .../endpoints/delete`) — for pruning garbage/noise traffic (a static asset request, a framework prefetch call) swept up during recording, with no other per-endpoint edit UI. Guarded by `useConfirm`; the confirmation label is built from the pre-run response row already on screen (`r.method`/`r.url`), NOT re-derived from `collection.json_content` — that list can lag behind what's actually rendered if the collection was refreshed elsewhere since the modal opened, which would otherwise show the wrong endpoint's name in the confirmation text. After a successful delete, `preRunData`/`ownCollections`/`logModalCollection` are all updated locally and `correlationsByCollection` is refetched (rule indices shifted server-side, not worth trying to patch up client-side).
- **Fixed: opening "Show Logs" alone always showed "Correlations 0", even when rules were safely persisted server-side.** The mount effects restore `preRunData` from a collection's persisted `pre_run_data` column, but `correlationsByCollection` was only ever populated as a side effect of calling `preRun()` (or a rule mutation) — never hydrated on a plain "Show Logs" click. Both "Show Logs" buttons now call `openLogModal(c)`, which fetches `GET /api/ai/correlations` fresh every time the modal opens, same as `preRun()` already did.

## Authentication

- JWT (HS256, `JWT_SECRET` env, 7-day expiry per `auth.js`'s `JWT_EXPIRES`; docs say 14-day — verify against `passwordReset`/`auth.js` at time of reading).
- Every token carries a `jti`; `user_sessions` tracks one active session per user server-side — logging in elsewhere invalidates the old session (`SESSION_ACTIVE` conflict unless `force: true` is passed). Session also expires after 30 minutes of inactivity, tracked via `last_used_at`.
- `middleware/auth.js` validates the Bearer token, checks the session row hasn't expired/gone stale, and updates `last_used_at` on every authenticated request.
- Passwords: bcrypt, 10 rounds.
- Roles: `super_admin` (all orgs), `org_admin` (own org's projects, can invite/approve), `user` (only explicitly assigned projects). Role checks are enforced both in route handlers and via `ownsProject()`.
- Secrets at rest (API keys, SMTP passwords, git PATs/SSH keys) are AES-256-CBC encrypted; never returned raw over the API (masked or presence-flagged instead).

## Business Logic — Notable / Non-Obvious

- **Postman `{{var}}` handling**: `parseCollection.js` stores the raw URL string as-is, including any `{{var}}` template text — it does **not** execute Postman pre-request scripts or resolve Postman environment/collection variables at parse time. Downstream, `testSuites.js`'s `normalizeEp()`/`toJmeterVar()` extracts just the **path** portion (discarding whatever precedes it, including `{{url}}`) and rewrites any remaining `{{var}}` in query params to JMeter's `${var}` syntax.
- **Added: multi-host JMeter script generation — a single collection covering several API families with different base URLs (e.g. Binance's Spot/Futures/Options/Wallet/Convert APIs, each on its own subdomain via a distinct `{{var}}`) now generates ONE JMX with multiple hosts, instead of forcing every sampler onto a single host.** This supersedes the earlier "each family must be a separate API Source" limitation for the common case where the multi-host-ness is expressed via distinct `{{var}}` tokens (still true if a collection mixes literal hostnames with no variable at all — that genuinely can't be disambiguated). `testSuites.js`'s new `resolveEndpointHost(rawUrl, variables)` resolves each endpoint's own leading `{{var}}` token against `cfg.variables` (the collection's harvested variable map — same one `collections.js`'s `seedEnvVariables`/`autoPopulateProjectConfig` populate) independently at generation time, grouping endpoints by distinct resolved `{protocol,host,port}`. `buildJmxTemplate()`/`buildSamplerXml()`: if only one distinct host is used, behavior is unchanged (plain `PROTOCOL`/`SERVER`/`PORT` UDVs, all samplers reference them). If more than one, it instead emits indexed `PROTOCOL_1/SERVER_1/PORT_1`, `PROTOCOL_2/SERVER_2/PORT_2`, ... (no plain/unindexed set — would just duplicate whichever host came first) and wires each `HTTPSamplerProxy`'s domain/port/protocol to the `_N` triplet matching its own endpoint's resolved host; an endpoint whose host can't be resolved (relative path, unknown variable) defaults to host `_1`. "HTTP Request Defaults" and the runtime-override XML comment (`-JSERVER_1=... -JSERVER_2=...`) follow the same indexing. Script generation's pre-check (`POST /:id/generate`) also now accepts "at least one endpoint resolves a host via `cfg.variables`" as satisfying the "has a target URL" requirement, not just a saved `collection_env_config.urls` entry — keeps a freshly-imported multi-host collection generatable even before `collection_env_config.urls` (a flat single-array field, not host-aware) catches up.
- **At script-generation time, the target host/port/protocol comes from Peako's own per-collection-per-env config (`envConfig.js` / `collection_env_config.urls` for the single-host default, `.variables` for multi-host per-endpoint resolution above) — never from a *literal* base URL embedded in the imported collection itself**, only from `{{var}}` tokens resolved against the collection's own variable map. A collection using literal (non-`{{var}}`) hostnames for different families with no distinguishing variable at all still can't be split automatically — import each such family as a separate API Source.
- **Fixed: importing a `{{var}}`-only collection (base URL only ever referenced as `{{alpha_url}}`, never literal) left that collection's `collection_env_config.urls` completely empty, forcing the user to manually type in the URL under Config > Environment Config even after uploading a Postman environment file that already had the real value.** `collections.js`'s `autoPopulateProjectConfig()` builds its hostname list by `new URL()`-parsing each endpoint's raw URL and skipping anything still containing `{{` — for a collection whose *every* endpoint uses a template base URL, this produced zero `urlSets`, so the function returned at line 46 before ever writing `collection_env_config` (see the CI-status/heal fix entry below for how this empty config then leaked another collection's URL into script generation). Fixed by resolving `{{key}}` tokens in each endpoint's raw URL against the collection's already-computed `collectionVariables` map (collection's own `variable` array defaults, overridden by an uploaded `.postman_environment.json` — the same map `seedEnvVariables()` stores) *before* the `{{`-skip check — `autoPopulateProjectConfig(projectId, jsonContent, collectionId, variables)` now takes that map as a 4th arg, passed from both `POST /` and `PUT /:id`. A collection like Binance whose endpoints are all `{{alpha_url}}/...` now gets its env config auto-filled with the real resolved host/protocol/port (port stays `''` if the variable's value didn't specify one) the moment it's imported — no manual Environment Config edit needed for the common case. Still manual-only when the base URL isn't captured by any variable or literal URL at all (genuinely no way to infer it). `configWriter.js`'s parallel `autoPopulateFromCollections()` (only touches project-wide `project_config`, a display-only reference value, not read by script generation since the collection-scoping fix above) was intentionally left as-is.
- **Pre-run `{{var}}` substitution (added)**: `collection_env_config.config_json` now supports an optional `variables: { [key]: value }` map alongside `urls`, keyed per collection+env like everything else in that table. It's populated two ways at collection import/update time (`collections.js`): (1) auto-harvested from the Postman collection's own top-level `variable` array if present (`extractCollectionVariables`), and (2) from an optional second file upload — a Postman `.postman_environment.json` export (`environment_file` form field, parsed by `parsePostmanEnvironment`) — whose values win over the collection's own defaults. Re-uploading a collection never clobbers variable values a user already has stored for an env (`seedEnvVariables` only fills in missing keys). `ai.js`'s `POST /pre-run` looks up the collection's **default** environment's variables (`collections.environment` — pre-run itself has no per-env selector in the UI today) and substitutes `{{key}}` in the URL/headers/body before the SSRF `isSafeUrl()` check and before firing the request; if a token is still unresolved after substitution, pre-run now returns a clear `Missing value for variable(s): x, y` skip reason instead of the old generic "URL blocked or invalid". Script generation's `{{var}}`→`${var}` behavior (above) is unchanged by this — this fix is specific to pre-run's live HTTP calls.
- **Pre-run used to hard-cap at the first 20 endpoints (`endpoints.slice(0, 20)`), removed**: now fires every endpoint in the collection, not a subset — this was a real, documented limitation (`docs/USER_WORKFLOW.md` used to say "up to 20"), not something the user was doing wrong. To avoid hammering the target server with a huge simultaneous burst on large collections, endpoints are still processed in bounded-concurrency chunks (`CHUNK_SIZE = 20`, same concurrency as the old single batch) with a 250ms pause between chunks, rather than one giant `Promise.all` over the whole list. Confirmed on a real 56-endpoint collection: all 56 fired (previously would've silently stopped at 20), completed in ~4.6s.
- **Pre-run was also never appending query params (separate bug, fixed)**: `parseCollection.js` stores an endpoint's query params separately (`ep.queryParams`, e.g. `{symbol: "BTCUSDT"}`) from its URL (`ep.url` has no query string). `ai.js`'s `fireEndpoint` only ever fetched `ep.url` directly, silently dropping every query param on every pre-run request — endpoints requiring a mandatory param (e.g. Binance's `symbol`) failed with `400`/`-1102 "Mandatory parameter ... was not sent"` even though the collection had the param stored. Fixed with `appendQueryParams(url, ep.queryParams, variables)` (builds `?k=v&...`, substituting `{{var}}` in values too) before firing — confirmed with a real Binance collection: fixed 400s across an entire API family and several others outright. Any params still failing afterward are almost always a genuinely different problem — the *value* stored is a Postman placeholder (e.g. `symbol_example`, `INTERVAL_1m`) rather than a real one, which surfaces as Binance's own validation errors (`-1121 Invalid symbol`, `-1120 Invalid interval`) — that's a collection data-quality issue to fix in the source values, not a Peako bug.
- **Some endpoints need a real API key even in a "no-signature" collection (known limitation, not a bug)**: Binance classifies some endpoints (e.g. `listenKey` management, futures `historicalTrades`) as needing an `X-MBX-APIKEY` header without needing a full HMAC signature — filtering a collection down to "no signature required" doesn't fully capture "needs zero credentials". Peako has no way to supply a real key for these (the stored header value is blank, not a `{{var}}` token, since Postman's own collection relied on a pre-request script to inject it, which Peako doesn't run) — they'll show `401`/`-2014 "API-key format invalid"` until a real key is wired into that specific header manually.
- **Pre-run** (`ai.js`) must be run and "fresh" (hash-matched to the current collection) before script generation is allowed — this gates `testSuites.js`'s `POST /:id/generate`.
- **Fixed: `{{var}}`-as-hostname pollution in the URL auto-populate logic**: `collections.js`'s `autoPopulateProjectConfig()`, `configWriter.js`'s `autoPopulateFromCollections()`, and `Config.jsx`'s frontend `autoPopulateFromCollection()` all independently did `new URL('https://' + rawUrl)` on every endpoint URL to seed `project_config`/`collection_env_config.urls` — with no check for `{{var}}` templates, this happily "parsed" e.g. `{{alpha_url}}` as a literal hostname and always defaulted its port to `443` (since no real port was ever present to parse), producing confusing garbage rows in the **Endpoint Details** panel (project-level `urls`, shown in Config.jsx when no collection/env is selected — a completely different, unrelated panel from the collection+env-scoped **Variables** section described above). - **Added: a token-efficient "diff patch" repair tier, `tryDiffPatch()`, tried before the full-script rewrite for every category the endpoint-override patch doesn't cover (`ZERO_SAMPLES`, `DNS_HOST_FAILURE`, `CORRELATION_PARAMETERIZATION`, `ASSERTION_FAILURE`, `UNKNOWN`).** The full-script rewrite's output size is bounded by the file's own size (it has to reproduce everything); a diff patch's output size is bounded only by the size of the *change* — the AI is asked for a small JSON list of `{find, replace}` surgical text edits instead of the whole file, so a fix to a 247KB script that only touches a few lines now costs roughly the same output tokens as fixing a 2KB script. `applyDiffPatch()` requires each `find` to match the script's current content **exactly once** — 0 or 2+ matches means that edit is rejected rather than guessed at (could silently corrupt the script or apply to the wrong spot) — and the same "no sampler may be dropped" guard the full-rewrite path already enforces is re-checked after patching. - **Fixed a real bug found via a live-generated JMX file: `buildSamplerXml`/`buildK6Request` (`testSuites.js`) unconditionally let a saved per-endpoint override (`endpointOverrides`, from pre-run's "Fix with AI") clobber a header that a CONFIRMED correlation rule already targets — same precedence bug already fixed for live pre-run (`ai.js`'s `/pre-run` Phase 2), but this one lived in script generation, a completely separate code path nothing there touched.** An override predating the rule commonly references `{{captured:X}}` for a field `capturedFields`/`detectCapturedFields` never covers (e.g. a cookie-sourced value) — the placeholder-translation regex (`applyOverridePlaceholders`) just leaves it as literal, unresolved `{{captured:X}}` text, which is syntax JMeter has never supported. So the override didn't just apply a *wrong* value, it baked invalid text directly into the generated script, overwriting what the correlation rule had already computed correctly for that exact header. Both header-merge sites now skip an override entry when a confirmed rule (`targetRules`) already targets that same header (case-insensitive); a body override or a header no rule touches is unaffected.
- **Added: correlation detection now also scans response HEADERS (not just the JSON body) as a source, and form-urlencoded bodies (not just JSON) on both source and target sides.** A value returned only via e.g. a `Location` header on a 201 Created, or a custom auth header, used to be invisible to detection entirely (`buildSourceIndex` only ever read `r.body`). `HEADER_SOURCE_DENYLIST` excludes boilerplate headers (`content-type`, `date`, `set-cookie` — cookies have their own dedicated capture path in `preRunEngine.js`, not this generic one) so indexing every header doesn't flood detection with noise. `parseBodyToObject()` parses `key=value&key2=value2` the same way as JSON, feeding the same `flattenToLeaves` pipeline; XML/multipart bodies remain out of scope (disproportionate effort for how rarely they appear in recorded API traffic). Wiring a header-sourced rule through to a script needed real, verified mechanics on both engines: JMeter's `RegexExtractor` needs `useHeaders=true` and a **case-insensitive** `(?i)` regex flag, because `preRunEngine.js`'s header capture (via the Fetch API's `Headers.entries()`) always lowercases names per spec, but the real target server's header casing at the script's own future runtime may differ — a case-sensitive regex built from the lowercased name would silently never match. k6 needs the equivalent case-insensitive scan of `res.headers` (`k6HeaderAccessor()`), for the same reason.
- **Added: `ai.js`'s `/pre-run/heal` (the AI-guided per-endpoint fix flow) now sees the full correlation field pool, not just the fixed `TOKEN_KEYS` list.** Its prompt used to be built from `extractAllTokens()` only — asking the AI to fix a failing endpoint that needed, say, `{{captured:orderId}}` would never even list `orderId` as an option. `describeAllCapturedFields(priorResults, endpoints)` (`correlationEngine.js`) now flattens every prior response's body AND headers, endpoint-attributed (so the AI can disambiguate a same-named field from two different endpoints), and merges into the same `capturedTokens` map `fireEndpoint()` already resolves `{{captured:KEY}}` against — the underlying substitution mechanism was already generic, only the field list feeding the prompt was artificially narrow.
- **Added: transform/derived-value correlation** (`transforms.js`) for a target needing a *derived* version of a source value (hash/case-change/encode), not a verbatim copy — e.g. "the target needs the md5 of the login response's userId." Always manually authored via `POST /ai/correlations/manual`'s optional `transform` field — a transformed value can never literally match anything, so auto-detection can never propose it. Deliberately a fixed whitelist (`md5`/`sha1`/`sha256`/`urlEncode`/`urlDecode`/`upperCase`/`lowerCase`), not arbitrary scripting, verified against JMeter's real function reference (confirmed `__base64Encode`/`__base64Decode` don't exist as native functions — excluded rather than shipped via an unreliable JSR223+Groovy fallback) and k6's `k6/crypto` module (imported into the generated script only when a rule actually needs it).
- **Fixed two real correctness bugs found while building the above (both predate this session's start, in the original manual-rule/query-param code, not introduced by it):** (1) A manually-created correlation rule never stored the target's *current* literal `value` — and `substituteCorrelatedLiterals`'s staleness guard only ever applies a rule when the live literal still matches `rule.value` — meaning **every manually-added correlation rule would silently never apply to anything**. `POST /ai/correlations/manual` now computes and stores the endpoint's actual current literal (via `extractRequestLiterals`), 404s if the target field doesn't exist, and accepts an optional explicit `value` override for a header that wraps the correlated part with a prefix (e.g. `Bearer <token>` — the substring to replace, not the whole header text). (2) **k6's query-string builder was percent-encoding query-param values unconditionally** — corrupting ANY `${...}` correlation/generator/transform placeholder placed in a query param (e.g. `${crypto.md5(x, 'hex')}` became `%24%7Bcrypto.md5(x%2C%20'hex')%7D`, sent to the server literally) since k6 folds query params into the URL for every method including GET, unlike JMX (which has a separate, unaffected code path for GET). Fixed via `isPlaceholderRef()` (`testSuites.js`) — a value already matching `^\$\{.*\}$` is passed through untouched instead of `encodeURIComponent`'d. Neither bug had ever been caught because no earlier fixture test happened to target a `query` location for a correlation rule.
- **Added: JMeter-parity script-generation features** (`testSuites.js`): (1) a per-request `ResponseAssertion` (status matches `[23]\d\d`) on every sampler, matching k6's `check()` — JMeter doesn't fail a sample on a non-2xx status by default, so this was a real gap; property keys verified against JMeter's own source, including a real typo baked into JMeter itself (`Asserion.test_strings`, missing an "s" — "fixing" the spelling would silently no-op the assertion). (2) a single `ConstantTimer` (1000ms) at Thread Group scope for request pacing, matching k6's flat `sleep(1)` between every request — a Timer at Thread Group scope applies to every sampler beneath it, so one declaration suffices. (3) nested Simple Controllers (`GenericController`) mirroring an endpoint's full recorded folder path (`folderPath`, e.g. "Users / Address"), not just the single top-level folder `detectCapturedFields` used to group by.

- **CSV test data** auto-copies across all environments if uploaded without a specific env.

## Coding Conventions

- Routes: Express `Router()` per resource, `router.use(auth)` near the top except where a route must stay public (invite validation, password reset, health check) — those files apply `auth` per-route instead.
- Authorization pattern: every project-scoped route calls `ownsProject(userId, projectId)` and 404s if it returns falsy (never 403 — avoids leaking existence).
- DB access: `db.prepare(sql).get/all/run(...params)` — SQLite-style call sites preserved even after the Postgres migration via the `pg.js` compatibility shim (auto-converts `?` → `$1`, appends `RETURNING id` to INSERTs). New Postgres-specific code should still use `?` placeholders, not `$1`, to stay compatible with this shim.
- Config-on-write pattern: mutating rules/config/collections triggers a `setImmediate`-deferred background rewrite of the affected workspace's `config.json`, not a synchronous one (keeps request latency low).
- No comments-heavy style; the codebase favors short inline comments only where a decision is non-obvious (e.g. SSRF guards, Windows-specific git auth workarounds).
- No TODO/FIXME/HACK markers found anywhere in `backend/src` or `frontend/src` at time of writing — the codebase does not use that convention for tracking debt.
- **The whole app renders at `html { zoom: 0.9 }`** (`index.css`) — "zoom:0.9 is the only way to scale ALL px/em/rem values uniformly," per the comment there. Only the login page overrides it back to `zoom: 1 !important` (so `100vh` behaves normally on `#auth-screen`). **This has a real, confirmed consequence for any code that reads `getBoundingClientRect()` and reapplies those pixel values to a `position: fixed`/`position: absolute` element** (portals especially): `getBoundingClientRect()` returns coordinates already scaled by the 0.9 zoom, but a fixed-position descendant of the zoomed `<html>` gets that raw pixel value re-scaled by the browser *again* when resolving its own position — a double-zoom. Confirmed by exact math: a computed `top: 341.469px` rendered at `307.3px` (341.469 × 0.9 = 307.3). Fixed in `CustomSelect.jsx` (its dropdown is portaled to `document.body`) by dividing every measured coordinate (`top`/`bottom`/`left`/`width`) by the current zoom factor (read via `getComputedStyle(document.documentElement).zoom`, not hardcoded, since it's `1` on the login page) before writing it into the portal's inline style. **Any new code that portals an element and positions it via `getBoundingClientRect()` needs the same zoom-correction — this is not specific to `CustomSelect`, it's a property of the whole app's zoom approach.**
- **Modal header/footer are sticky by default (global CSS, not per-modal JSX)**: every standard modal in the app follows the shared `<Modal>` (`components/Modal.jsx`) + `.modal-hdr` + arbitrary content + `.modal-footer` structure, and `.modal` itself is the scrolling container (`overflow-y: auto`). `.modal-hdr`/`.modal-footer` in `index.css` use `position: sticky` (with the negative-margin/matching-padding trick to stay flush with `.modal`'s own padding) so close icons and action buttons never scroll away regardless of content length — this was a deliberate fix (previously they scrolled with the content). New modals get this for free automatically as long as they use the standard `.modal-hdr`/`.modal-footer` classes; don't reinvent scroll handling per-modal.
- **Exception — custom draggable/resizable popups don't use `<Modal>`**: e.g. Collections.jsx's "Pre-run Logs" window is hand-built (`position: fixed` overlay + `position: absolute` box with its own drag handle and `resize: both`), not the shared component, so it doesn't inherit the sticky-header CSS above. It replicates the same look/behavior manually with three stacked flex children, each `flexShrink: 0` except the middle one: a fixed header (drag handle + title + close icon), a scrollable body (`overflowY: 'auto', flex: 1, minHeight: 0`), and a fixed footer (border-top + right-aligned `btn-primary` "Close" button, styled to match `.modal-footer` visually without reusing that class directly — `.modal-footer`'s sticky/negative-margin CSS is tuned for `.modal`'s own padding box and would misbehave outside it). The body only actually scrolls if the outer box has a height ceiling — it originally had none (only `minHeight`), so long content just grew the whole popup past the viewport instead of scrolling. Fixed with `maxHeight: calc(100vh - ${logModalPos.y}px - 24px)` (dynamic, tied to the popup's current drag position `logModalPos.y`) rather than a flat value — a flat cap (e.g. `80vh`) would make the native `resize: both` handle feel broken once content reaches it, since height can never be dragged past a fixed ceiling regardless of how much empty space is actually below the popup. **`max-height` alone wasn't enough**, though: with no explicit `height`, the box only auto-sized to its content and left unused space below rather than stretching to fill the available room — an explicit `height: ${Math.min(620, window.innerHeight - logModalPos.y - 24)}px` (plain JS-computed pixels, not a nested CSS `min()`/`calc()` — some environments choke on `min()` wrapping `calc()`) was needed so the body's `flex: 1` has an actual bounded space to grow into. The header drag handler (`onLogDragStart`) also clamps `y` to `Math.max(0, ...)` so the popup's top can never be dragged above the visible viewport. Any future custom (non-`<Modal>`) draggable popup needs all three: an explicit `height` (not just `max-height` — `flex: 1` + `overflow-y: auto` on a child does nothing without a bounded parent height to grow into), a `max-height` ceiling, and a drag-position clamp to stay on-screen.

Fixed: SSH-mode unchanged; PAT-mode now opens the same `gitEngine` session (`git_configs.git_root`/`projects.folder_path`) and writes the fix there, `persistSession`-flushed to S3. (The endpoint-override fix path needed no change at all — `applyEndpointOverrides()` is pure `collection_env_config` DB writes, never touches the script file.)
3. **`execution.js`'s hard-delete route (`DELETE /runs/:id?delete_files=true`) never actually deleted anything from S3** — its `fs.rmSync(run.result_dir)` was `existsSync`-guarded, and since `result_dir` has been S3-only since the earlier `resultsStore.js` migration, that guard was always false — a silent no-op that left every hard-deleted run's JTL/report/PDF orphaned in the bucket forever, with the DB row gone and no way to find them again. Fixed to call `resultsStore.deleteAll(run.result_dir, orgSlug)` (real S3 prefix delete) instead of touching `fs` at all.
4. **Investigated and deliberately left alone** (not disk-write bugs, different problem shapes):
   - `projects.js`'s `DELETE /:id` background cleanup — its GitHub-removal step is gated by `fs.existsSync(gitCfg.git_root)`, which is already always `false` for PAT-mode (no real path ever exists there) — so it correctly no-ops today rather than writing incorrectly. The real gap is a **missing feature**, not a bug: a PAT-mode project's GitHub repo is never cleaned up on project delete. Its backup step (`backupAndDeleteProjectFolder`) was already fixed in an earlier session (S3-aware via `ownerUserId`).
   - `execution.js`'s `POST /run`, `pipelines.js`'s `POST /:id/run`, and `autoHealer.js`'s native `startAutoHeal`/`healCycle` — all confirmed genuinely dead code (hard `return`/`res.status(410)` before any of the disk-writing logic executes; native/local test execution was retired outright in Phase 1). Not touched — fixing unreachable code has no effect and these are explicitly, intentionally retired.
   - `generateAnalyticsPdf.js`/`trend/exportEngine.js`'s `fs.unlinkSync` calls, and `testRunner.js`'s writes — ephemeral `os.tmpdir()` Puppeteer screenshots (unrelated to project data) and native-execution-only code (same retired path as above), respectively.
5. **Verification**: full `node -r dotenv/config --test "src/**/*.test.js"` — 169/169 passing (the earlier flaky `collection_env_config` sequence-collision test passed cleanly this run). **`/trigger`'s new PAT branch verified live** against a real local git-smart-HTTP remote + the real `peako-dev` bucket, specifically exercising the hardest case: a genuinely diverged history (a local un-pushed commit *and* an independent remote push) — confirmed the `fastForwardOnly` merge correctly threw, `resetHardToRef` correctly discarded the local-only commit while a *separately preserved* uncommitted tracked-file edit survived and ended up in the final pushed commit, and a fresh third session read the identical state back from S3 alone. One real bug caught only by this live run (not by `node -c`/the unit suite): `resetHardToRef` was implemented but never added to `gitEngine.js`'s `module.exports` — fixed immediately after the live test surfaced it.

**Phase 6 — `gitEngine.js`'s `openSession`/`persistSession` no longer round-trip the WHOLE workspace on every save (this session, uncommitted; user-reported: saving config became noticeably slower than the old local-disk days).** Root cause: every PAT-mode write — a single `config.json` save via `configWriter.js`'s `writeJsonToSession`, a rules sync, a test-data upload, anything — called `openSession()` (downloads **every file** in the user's whole per-project workspace, one `GetObject` each, unbounded parallel) then `persistSession()` (re-uploads **every file**, unconditionally, even ones nothing touched), just to change one file. Fixed with two changes, both internal to `gitEngine.js` — no caller (`configWriter.js`, `collections.js`, `rules.js`, `testData.js`, `testSuites.js`, `git.js`, `ciPipeline.js`, ~30 call sites total) needed to change:
- **In-process byte cache** (`sessionByteCache`, keyed by the workspace's S3 base key, `GIT_ENGINE_SESSION_CACHE_TTL_MS`-bounded, default 15 min, swept on a background `unref()`'d timer): `openSession()` serves from cached buffers when warm — zero S3 calls at all — instead of re-downloading. Each call still gets its own **private** `memfs` Volume built fresh from those cached bytes, so concurrent requests never share a live mutable volume and can't corrupt each other's in-flight git operations — only read-only source bytes are shared.
- **Dirty-diff on persist**: `persistSession()` now hashes current file content against the baseline captured at `openSession()` time and uploads only new/changed files, deletes only files that were removed (a `s3Sync.deleteKey()` raw primitive, new), and skips S3 entirely if nothing changed — which also makes the pre-existing pattern of calling `persistSession()` two-or-three times in one request (several `git.js`/`ciPipeline.js` routes do this) free after the first real flush, instead of re-uploading the same unchanged tree each time. Fixes a latent bug as a side effect: the old unconditional-reupload persist never deleted anything from S3, so a file removed from the working tree used to linger in S3 forever and reappear on the next hydrate.
- `invalidateCache(gitDir, orgSlug)` (new export) is called from `projectFolders.js`'s `backupS3Workspace()` right after its tombstone delete, so a project-delete's direct `s3Sync.deleteAllUnderPrefix()` (which bypasses gitEngine entirely) can't leave stale cached bytes behind for a workspace path that gets reused.
- Single-process assumption (same as `workspaceLifecycle.js`'s old SSH-mode disk cache) — correct for the current single-instance Docker Compose deployment; would need a shared cache to stay correct across multiple replicas behind a load balancer.
- **Verified** via a scratchpad harness faking `s3Sync`'s network calls with an in-memory store + call counters: cold open downloads every object once; a single-file edit + persist issues exactly one `PutObject`; a second, redundant `persistSession()` on the same session makes zero S3 calls; a second `openSession()` within the TTL is served entirely from cache (zero S3 calls) and sees the first session's edit; removing a file + persist issues exactly one `DeleteObject`, zero uploads. Also re-ran `node -r dotenv/config --test src/utils/workspaceLifecycle.test.js src/utils/opsAlert.test.js` — 12/12 passing, no regression.

**Fixed a real bug in `/generate-yaml`'s own Phase 4 fix, found via live user repro (this session, uncommitted): regenerating YAML a second time failed with "Push rejected ... not a simple fast-forward."** The PAT branch's `checkout(session, autoCommitBranch)` is a same-session no-op once that branch already exists in the persisted session (true on every call after the first) — it never looked at the remote at all before pushing. If origin advanced since the session was last persisted (someone pushed directly on GitHub, a `/trigger` run, etc.), the push was rejected exactly like `/trigger`'s auto-push already had to handle. Fixed by adding the identical fetch → `fastForwardOnly` merge → `resetHardToRef`-fallback sync step (with the same preserve/restore-uncommitted-edits guard) between the branch-checkout and the file-write step, mirroring `/trigger`'s already-proven logic exactly. **Verified live**: reproduced the exact failure first (first call succeeds, then an independent push to the real bare remote, then a second call throws the same "not a simple fast-forward" error) — then confirmed the fix makes the second call sync and succeed instead, with the independently-pushed commit preserved in history (a real merge, not a force-push) and the regenerated YAML content landing correctly on the remote.
